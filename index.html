The practice

What I'm hired for

Four things, and they are usually the same job seen from different sides. The through-line is that an agent which behaves well under supervision tells you almost nothing about how it behaves at 3am in week eleven.

Agents that run unattended

Long-running loops that decide and act with nobody in the chair: state that is derived rather than remembered, obligations wired into the runtime instead of written into a prompt, and a resume path that survives a context reset in the middle of a task.

Tool and MCP architecture

Designing the tool surface an agent actually calls, including the unglamorous parts that decide whether it works: what a tool returns when it half-succeeds, where a timeout lands, and how the model is stopped from narrating a failure as a success.

Guardrails and refusal design

Enforcement at the chokepoint — an exit code, a tool deny, a hook that blocks the turn from ending — rather than instructions the model is trusted to follow. Including the honest half: which guards can be routed around, and by what.

Evaluation and measurement

Control groups for agent behaviour, replay harnesses that score decisions against blinded historical data, and pre-registration so a result cannot be quietly reshaped after it arrives. This is the layer most agent projects skip, and the one that tells you whether you have anything.

I build largely by directing AI coding agents, which is its own discipline and is exactly what everything below is about. The systems are mine end to end — architecture, implementation, operation — and the audit trail for every one of them is written down.

An AI agent operating unattended against a live account

An orchestrator that reads live market data, forms a view, arms conditional triggers, submits real orders through an MCP tool surface, and then scores its own decisions after the close and feeds that back into how the next session runs. It has been running and evolving daily since April.

What it took

Two MCP servers in production. One built from scratch: seven tools over a swappable broker backend, a dedicated safety layer that sits between the model and the order, and its own integration bench simulating broker timeouts, rate limits and kill-switch fire. One third-party server patched in place, because its behaviour was wrong in a way that mattered and waiting for upstream was not an option.

Around that: a per-turn operating contract injected at prompt time rather than remembered, so a context reset cannot silently drop it. Position state derived from the broker on every read instead of from the agent's own log. Lifecycle hooks that refuse an action outright at the point of action — under a hard cap, because the interesting constraint is not adding guards but keeping them few: at most eight things may ever block a trade, and adding a ninth requires retiring one. A delegation layer that routes judgment-dense work to separate model seats with their model and reasoning effort pinned in version control, so a spawned worker cannot silently inherit the wrong configuration. Memory and retrieval designed to survive a fixed context budget across months. And a session-completeness contract, validated against a schema, that refuses to close a session with an artifact missing.

A falsification pipeline where the specification is frozen before it runs

The current work. An offline pipeline that takes a hypothesis, freezes its full specification as a SHA-256 hash in an append-only, hash-chained registry before anything executes, and refuses to run at all if the spec's hash no longer matches the record. Every result lands in the same ledger as the claim it tests, alongside the sensitivity bound that limits what it is allowed to conclude.

What it took

A findings ledger now past three hundred entries, each one carrying its evidence and its own limits. Gauges that read the ledger rather than a summary of it — and a regression test asserting that a retraction is actually representable, added after discovering that an append-only log plus a read-every-row-as-current gauge are individually reasonable and jointly incapable of reporting that something was withdrawn. A stopping rule signed in advance and enforced in code, so the programme can be closed by evidence instead of by mood. An adversarial review seat that never sees the author's reasoning, because self-graded review is not review.

An automated research platform, and the simulator that judged it

A strategy-discovery factory running roughly nine hundred and fifty search cycles over years of tick data, sitting on top of an execution simulator built specifically to be honest about fills, latency and cost, with a live execution tail deployed to a Chicago VPS. Four months, and the most useful thing it produced was a method, not a result.

What it took

Distributed Python pipelines, a full validation stack — combinatorially symmetric cross-validation, probability of overfitting, walk-forward, bootstrap and placebo comparators — and around sixteen hundred automated tests. Those tests still pass today on a repository untouched since June and on a newer Python than it was written for, which is the only test-suite claim I consider worth making.

The decisive contribution was learning to distrust the referee rather than the result, which is the finding written up further down this page. The programme was then closed against a stopping rule that had been frozen by hash before any real data was fit, reviewed by four independent adversarial passes, and its infrastructure torn down to zero cost the same day. Closing something deliberately, on a rule written before you knew the answer, is a skill; it is also the reason the next system starts with pre-registration built in.

Architecture

How an unattended loop is actually put together

The shape below is the one I keep rebuilding, in trading and outside it. Two details carry most of the weight: state is read from ground truth on every pass rather than carried forward in the model's own summary, and the places where the system can refuse are explicit, few, and sit on the path itself rather than in the instructions.

Field report

Nouns rot. Verbs hold.

What follows is the part of the work I would actually want judged: a set of findings that each came from something specific going wrong on a system where being wrong had a consequence, written down at the time, with the evidence that produced them.

Most agent portfolios are demos that have never been wrong in a way that cost anything. This one had a loss function from the first week, and it was not a metric I chose.

A defect with a price attached

A stop-loss placed inside a recently swept price wick cost $846 on a single order. The fix was not a warning and not a note in a document. It became an arithmetic gate that rejects the order outright when the stop is not beyond the supplied wick extreme — and it was verified by replaying the exact trade that produced the loss and confirming that the gate now refuses it. That replay is the difference between a fix and a claim of a fix.

The core finding

Every fix sits on a durability ladder, and almost everyone mis-rates their own

Across twenty-seven tracked fixes, roughly half held and half decayed — and the split fell cleanly along one axis. Not correctness. Not importance. The location of authority.

The permanence test

Does the fix still hold for an actor who never read it?

A fresh context inherits the codebase's behaviour and never an instruction's force. Any fix whose enforcement is “the actor reads X and chooses to comply” is a noun with extra steps. It will rot the first session the actor is under time pressure or has not loaded X.

And the top rung is conditional

The hardest lesson here came from being wrong about it. We removed an affordance — a browser tab that could be disturbed mid-job — and declared that whole class of bug impossible. It recurred. The removal was itself an action someone had to perform, and on a path nobody had walked it never ran.

So the real test is stricter than it first looks: is the affordance never created, or is its removal a verb that fires regardless of which path the actor took? A removal-by-action is rung 2.5, and it fails exactly where you never walked.

Three findings underneath that one

A verb guards an action; a rule names a behaviour

“Don't disturb a running job” has at least three action-faces: kill it, touch it, over-poll it. We guarded the kill face, marked the behaviour fixed, and the touch face — still naked, still a noun — failed weeks later. When you convert a behaviour into a verb, enumerate every face it covered and either guard each one or write down explicitly which remain unguarded. Guarding one face and declaring victory is precisely how a fixed bug comes back.

The fix ledger is write-only unless recognition has a chokepoint too

The deeper problem is not that fixes rot. It is that at the moment of recurrence, the lookup have we seen this exact thing before? never fires. We recorded six dated recurrences of one bug, beautifully, and read none of them while diagnosing the seventh. Recognition needs a trigger on the path, or you will re-diagnose solved problems indefinitely.

Delegate the work, never the clock

Nothing self-re-animates a dormant agent. I tried an inline sleep; it returned early. I tried leaving a live background child and expecting the parent to wake on its completion; it did not. The durable form of “continue this later” is the foreground being re-invoked by an automatic harness event — a scheduled wake, a cron, a task-completion callback. This is the permanence test in its concurrency form, and it cost several silent no-ops to learn.

The hardest case

Every guard has a ceiling, and the pattern in those ceilings is the finding

The system's second job was enforcing a limit against a human operator whose judgment is compromised at exactly the moment the limit matters. This is the permanence test with the difficulty turned up: the actor does not merely forget the rule, he is motivated to route around it.

I built five mechanisms across five weeks and put each one in front of live conditions. Every one has a real ceiling; each is dated and recorded next to the claim it corrected. This is the table I would want any client with an agent in a sensitive path to read before they trust their own guardrail.

The finding that generalizes

A partial block does not stop the behaviour. It herds it into the channel you cannot see.

That last row is the one I would carry into any system with a human or an agent in the loop. Every constraint added to the observed path raises pressure on the unobserved one. Enforcement covering most of the surface does not buy you most of the protection; it buys you the same behaviour, now invisible, and usually larger. Defend the resource, not the interface.

What did hold

Not a lock. A layered posture, correctly labelled. Friction that announces itself — a re-entry path that takes ten minutes and cannot be done quietly, which breaks the two things the behaviour runs on, speed and secrecy. A single instrumented channel, so every action lands on one recorded surface and diagnosis afterwards is possible at all. And ground-truth measurement: judge by the broker's own balance, never by the system's log, because the path you care about leaves no rows in it.

Cut by our own data, before shipping

Loss-streak locks, post-loss cooldowns and a proportional give-back ratchet all sounded right. Replayed against real recorded sessions, every one of them fired repeatedly on healthy days. Better: the ratchet's original simulation was found to contain look-ahead bias — it computed its floor from the day's final high — and replaying it honestly tripped the very day that had been used to justify it.

All three were cut. What shipped instead was derived from the replay: a flat threshold, a rapid-reversal fuse and a size sentinel. When one of them first fired live, the falsification held up too — the cadence brake we had rejected would have made that day worse, cutting the session's two largest winners out of the run.

The layer underneath

Your evaluator is the thing most likely to be lying to you

Everything above is about making behaviour hold. This is about whether the evidence you used to decide was real in the first place, and it comes from the earlier research platform — the one that searched for strategies automatically and scored them against a simulator.

Its flagship candidate came back with Sharpe 13.76, probability of overfitting 0.0%, deflated Sharpe 1.0000. Every standard referee passed it. It did not survive contact with live execution.

The search was not broken. The search was optimizing against a simulator with a defect — and the overfitting statistics were computed inside that same defective simulator. Re-run on an honest execution model over the identical 89 sessions, the same candidate inverts completely: Sharpe −1.69. The backtest had been faithfully describing an engine that did not exist.

Three laws, each with a price attached

  • An optimizer converges on your evaluator's defects, not on your objective. Goodhart is not a risk to mitigate; it is the default output of any search loop given enough iterations.
  • Standard referees check the return side and cannot see a violation on the signal side. A separate screen passed bootstrap, placebo, a comparator and all thirteen trigger years at +150bp. One look-ahead field removed, it went to −9bp — indistinguishable from doing nothing. Only an information-set audit catches that class of defect.
  • A green test suite certifies capability presence, not operational effect. 1,571 passing tests covered sixteen self-improvement mechanisms. In a real multi-hour run, two of them fired. The rest were wired, enabled, tested and inert — most of them killed by a single silently-empty collection at an adapter boundary.

What worked was inverting the order: validate the validator against a known null before trusting any positive. Synthetic driftless data, the full gate stack, roughly 66,000 trades, zero survivors out of thirty. On data with no edge in it, the evaluator manufactured none. And that pass was recorded with its own honest bound: 0/30 constrains the false-positive rate to about 10%, and no better.

If you run an agent loop against an LLM judge or a synthetic eval, this is your problem, not a trading problem.

The loop will find your judge's blind spots faster than it finds the behaviour you asked for. That is not a warning about a rare edge case; it is the modal outcome, and it is why the pre-registration machinery in the current work exists.

The measurement

I built the control group for my own judgment

Across 409 recorded decisions, the system had never scored what it rejected. Every gauge measured the calls it took, so the question underneath all the others — is the selection carrying any information at all? — had never actually been asked. So I built the instrument that could ask it: each real decision scored against random entries drawn from the same day, the same direction and the same stop distance, differing only in which minute was chosen.

A clean answer, and worth stating precisely rather than dramatically: at that sample size, no effect is detectable — which is not the same claim as “there is none,” and the interval says exactly how large an effect would still have been missed. That is the whole value of building the control. It was the first result in the project that could redirect the programme rather than decorate it, and it did: discretionary live decision-making was narrowed, learning moved offline where a rule can be pre-registered and killed cheaply, and every hypothesis now freezes its specification as a SHA-256 hash in an append-only, hash-chained registry before it may run. The runner refuses to execute if the spec's hash no longer matches the record.

Then the new instrument tried to fool me, twice, in one evening

First real use: three textbook mechanical rules, fully specified and frozen in a commit before anything ran. One came back at 0.725, its confidence interval clear of chance — a survivor on the first attempt, which is exactly the result I was hoping for.

It took one question to kill it. Is this measuring the moment the rule chose, or just where in the local price range it happened to enter? Under a fixed stop with no profit target, an entry below its neighbours has a shorter stop and a longer run to the close — it beats them arithmetically, whether or not it predicted anything. Every rule's score turned out to be reproduced by entry-price position alone.

Read the third row: the “best” rule was in fact the one wasting the most favourable entries it had been handed. Once the control matched on price as well as on time, all three collapsed toward chance and the survivor was withdrawn — into the same append-only ledger that had recorded it, because a registry you can quietly edit is not evidence of anything.

And the dashboard kept reporting the dead survivor

The pace gauge counted every survived row as current, so appending the withdrawal left the headline still reading survivors: 1. An append-only ledger and a gauge that treats every row as current are each individually reasonable and jointly incapable of representing a retraction — the pair could only ever overstate. Fixed to take the latest verdict per candidate, proved by mutation, and given a regression test that asserts both values: reported while it stands, gone once withdrawn.

Three further false findings surfaced the same night in the data layer, each one caught by running a check rather than by reading it: an integrity gate excluding the primary instrument over “weekend” bars that were a timezone convention of my own; a table appearing to show older market history degrading in quality, where every degraded year turned out to be a public holiday; and a cross-feed price comparison reporting a fourteen-point disagreement, because it compared one feed's closing price against the other's within-minute average.

A control group that differs from the treatment in more than one way measures the difference you did not intend.

If you A/B test agent behaviour, or score a model against an LLM judge, this is the failure mode most likely to cost you: not a broken metric, but a well-built one whose comparison arm quietly differs on a second axis. The tell is that the result is the one you wanted and it arrived sooner than expected. Every number above was produced, published and refuted by the same system inside one evening, and all of it — the survivor, the withdrawal, and the sensitivity bound attached to each kill — sits in one hash-chained file whose row count is the multiplicity denominator.

Governance

Letting an agent modify its own machinery without letting it ratchet

The agent designs and implements its own tooling. That removes the natural over-build alarm, so the constraints have to be structural rather than tasteful.

  • A hard budget on blocking rules. At most eight things may ever refuse a trade. Adding a ninth requires retiring one. Enforced by an audit that runs at every session close, not by good intentions.
  • Tiered change authority. Reversible bug fixes ship autonomously. Parameter tunes ship but are logged. Any new per-turn artifact, gate or mechanism requires an explicit proposal. Critically: what a change touches sets its tier, not how the agent narrates it. “It's only a knob” is not a downgrade.
  • Bright lines that stay proposal-only, permanently. Capital values, the risk rules, the enforcement budget, anything irreversible.
  • External, non-self-graded refutation. Any significant design is attacked by a fresh context that never saw the design's framing, given only the proposal and the project's known anti-patterns and told to break it. The verdict is pasted in verbatim. The author does not get to write its own opposition.
  • Ship the gauge with the mechanism. Every mechanism carries at least one outcome-based success criterion. “The gauge fired” is not evidence. An audit fails the build if a decision record declares a gate without shipping its measurement.
  • Automatic suspension. The grant revokes itself if per-turn surface grows without an approved budget raise, if anything ships without its gauge, or if results regress alongside self-authored mechanisms.

The first change made under this charter was reviewed by an external pass, found to be redundant and built on a false premise, and reverted to zero net code. That is the charter working, not failing.

The habit underneath all of it

The single highest-value practice was periodically auditing the system's claims about itself and writing down where they were false, in place, next to the claim being corrected.

From the enforcement registry, verbatim

The prior “audit auto-demotes unused rules” clause was false — the field it depended on is empty on every item and no code reads it. Retirement is a manual hand-edit. Do not build the auto-demote; the diagnosis itself warns that such criteria “existed on paper and were never exercised.”

Elsewhere: a rule set documented as enforced was audited and found to be enforced in three places, advisory in a fourth, and entirely absent in a fifth — and the document was rewritten to say so, in bold, rather than quietly patched. Every significant decision record names its own blind spots, its confounds, and the evidence that would invalidate it.

This matters more in agent systems than anywhere else I have worked, because an agent will confidently narrate an obligation as satisfied. Every claim of “done” that is not derived from ground truth is a claim you will pay for later.
